# Модель данных Nawigator: зачем нужна каждая таблица

Концепция взята из [README.md](README.md). Модель реляционная и рассчитана на Oracle: 30 таблиц, 43 внешних ключа.
Ниже по каждому узлу диаграммы расписано, **зачем** он нужен и **почему** устроен именно так.
В скобках указаны функции (F-xx) и разделы (§) README, которые он закрывает.

Почему таблиц 30, а не 20–25 из §8. README считает 20 базовых таблиц и не включает в это число справочники из §10:
группы гражданства, страны, основания и цели пребывания, формы занятости (+5). Из необязательных расширений §8 взяты права
(PERMISSIONS, ROLE_PERMISSIONS) и помощник (HELPER_ACCESS, HELPER_NOTES). Отложены напоминания (это §13, после MVP)
и отдельная таблица групп AND/OR: её заменяет колонка `PROCEDURE_DOCUMENTS.ALTERNATIVE_GROUP`.

## Общие решения

| Решение | Почему |
|---|---|
| `ID NUMBER(10) GENERATED BY DEFAULT AS IDENTITY` | Ключ без ручных sequence и триггеров. `BY DEFAULT` разрешает вставлять фиксированные ID при начальной загрузке справочников. |
| Связочные таблицы: PK из двух FK | Пара не повторяется, суррогатный ID не нужен. |
| `VARCHAR2(n CHAR)` | Длина считается в символах, а не в байтах: польские буквы и кириллица в AL32UTF8 занимают по 2 байта. |
| Флаги `NUMBER(1)` + `CHECK (x IN (0, 1))` | Тип BOOLEAN в таблицах появился только в 23ai, а так схема работает с 12.2 по 23ai. |
| Статусы: `VARCHAR2` + `CHECK` | Набор фиксирован и зашит в логику приложения, поэтому справочник не нужен. |
| Индексы на FK (`IDX_*`, 34 шт.) | Oracle сам их не создаёт. Без индекса `ON DELETE CASCADE` и join'ы сканируют всю дочернюю таблицу и блокируют её. Индекс не создаётся там, где FK уже ведущая колонка PK или UK. |
| `ON DELETE` | `CASCADE`: строка не имеет смысла без родителя (данные клиента при удалении аккаунта, F-04, RODO). `SET NULL`: запись переживает автора (журнал, `VERIFIED_BY`). `NO ACTION` для справочников: нельзя удалить используемое значение. |
| Имена | Английские, в верхнем регистре, не длиннее 30 символов: `PK_<TABLE>`, `UK_/FK_/CK_/IDX_<сокращение>_<что>`. Сокращение (USR, PRC, DOC…) однозначно указывает на таблицу. |
| `COMMENT ON` | У каждой таблицы и у неочевидных колонок есть комментарий. Он виден в Data Modeler и в словаре БД. |

## Колонка 1. Справочники осей профиля

### CITIZENSHIP_GROUPS
- **Зачем:** группа гражданства (EU_EEA, NON_EU, UKRAINE, POLAND, POLISH_ORIGIN). Правила различаются именно по ней, а не по конкретной стране (§2).
- **Почему:** правило пишется один раз на группу, а не на 190 стран. Новая группа добавляется новой строкой, без изменения кода (§6 п.2).
- **Связи:** ← COUNTRIES, ← AVAILABILITY_RULES.

### COUNTRIES
- **Зачем:** справочник стран. Гражданство клиента (обязательное поле, F-02) ссылается сюда.
- **Почему:** колонка `CITIZENSHIP_GROUP_ID NOT NULL` однозначно выводит группу из гражданства. `ISO_CODE` уникален, поэтому справочник можно загрузить из стандартного списка ISO 3166.
- **Связи:** → CITIZENSHIP_GROUPS, ← USER_PROFILES.

### RESIDENCE_BASES
- **Зачем:** основание пребывания (виза, karta pobytu, регистрация гражданина ЕС, спецстатус Украины). Вторая ось правил (§2).
- **Почему:** это таблица, а не текстовое поле. Профиль и правила ссылаются на одно и то же значение через FK, и администратор правит справочник без изменения кода (§4.5).
- **Связи:** ← USER_PROFILES, ← AVAILABILITY_RULES.

### RESIDENCE_PURPOSES
- **Зачем:** цель пребывания: работа, учёба, бизнес, семья, возвращение. Третья ось правил (§2).
- **Почему:** то же, что у RESIDENCE_BASES. Цель и основание — разные оси: со студенческой визой можно и учиться, и работать.
- **Связи:** ← USER_PROFILES, ← AVAILABILITY_RULES.

### EMPLOYMENT_TYPES
- **Зачем:** форма занятости: umowa o pracę, umowa zlecenie, JDG, без занятости (F-02).
- **Почему:** от неё зависят шаги ZUS и CEIDG. Предпринимателю нужны другие процедуры, чем наёмному работнику (сценарии 2 и 4, §7).
- **Связи:** ← USER_PROFILES, ← AVAILABILITY_RULES.

## Колонка 2. Профиль, правила, языки

### AVAILABILITY_RULES
- **Зачем:** определяет, кому доступна процедура (F-06, F-20). Строка задаёт комбинацию осей. `NULL` в оси означает «любое значение», а `IS_ALLOWED = 0` — явное исключение («недоступно гражданам ЕС»).
- **Почему:** правила хранятся в данных, а не в коде, поэтому новая группа пользователей — это новая строка (§6 п.2). Таблица отделена от PROCEDURES, потому что у одной процедуры бывает несколько правил.
- **Связи:** → PROCEDURES (CASCADE: правила уходят вместе с процедурой). → четыре справочника (NO ACTION): иначе после удаления значения справочника правило молча исчезло бы, и процедура стала бы доступна всем.

### USER_PROFILES
- **Зачем:** ситуация клиента: гражданство, основание и цель пребывания, занятость, язык, выбранная жизненная ситуация, дата приезда. По профилю генерируется план (F-02, F-03, F-05, F-06).
- **Почему:** связь с USERS 1:1 (`PK = USER_ID`). USERS отвечает только за вход в систему, а профиль меняется часто и при каждом изменении пересчитывает план. `COUNTRY_ID NOT NULL` — это критерий F-02: без гражданства регистрацию не завершить. Остальные оси допускают NULL, потому что человек может их ещё не знать. От `ARRIVAL_DATE` считаются сроки «от дня приезда» (§7).
- **Связи:** → USERS (CASCADE), COUNTRIES, RESIDENCE_BASES, RESIDENCE_PURPOSES, EMPLOYMENT_TYPES, LANGUAGES, LIFE_SITUATIONS.

### LANGUAGES
- **Зачем:** языки интерфейса и контента: PL, EN, RU (§3, F-15).
- **Почему:** `FALLBACK_LANGUAGE_ID` ссылается на эту же таблицу и задаёт язык-заместитель на случай, когда перевода нет (например RU → EN → PL). Цепочка настраивается данными. `IS_ACTIVE` позволяет готовить язык, пока он скрыт от пользователей.
- **Связи:** → LANGUAGES (fallback), ← USER_PROFILES, ← TRANSLATIONS.

### TRANSLATIONS
- **Зачем:** перевод любого текстового поля любой таблицы контента: `ENTITY_TYPE + ENTITY_ID + FIELD_NAME + LANGUAGE_ID → TRANSLATED_TEXT` (F-21).
- **Почему:** одна общая таблица вместо отдельной `*_TRANSLATIONS` для каждой контентной таблицы, и новый язык не меняет схему. Плата за это: на `ENTITY_ID` нет FK (полиморфная ссылка), целостность обеспечивает приложение. `UK_TRN_ENTRY` запрещает два перевода одного поля на один язык. Базовый польский текст хранится в самих таблицах.
- **Связи:** → LANGUAGES.

## Колонка 3. Доступ и аудит

### PERMISSIONS
- **Зачем:** атомарные права (`PROCEDURE_EDIT`, `USER_BLOCK`…), которые сервер проверяет при каждом запросе (§4).
- **Почему:** сервер проверяет конкретное право, а не название роли. Поэтому роль можно расширить без изменения кода. Это расширение из §8 («Po dodaniu uprawnień baza ma 22 tabele»).
- **Связи:** ← ROLE_PERMISSIONS.

### ROLE_PERMISSIONS
- **Зачем:** какие права есть у какой роли (M:N).
- **Почему:** составной PK `(ROLE_ID, PERMISSION_ID)` не даёт выдать одно право дважды.
- **Связи:** → ROLES, → PERMISSIONS (обе CASCADE).

### ROLES
- **Зачем:** роли CLIENT, HELPER, EDITOR, ADMIN (§4). Gość — не роль: у гостя нет аккаунта.
- **Почему:** роли хранятся в таблице, как требует §4. У пользователя ровно одна роль. Администратор получает права редактора через ROLE_PERMISSIONS, второй роли для этого не нужно.
- **Связи:** ← USERS, ← ROLE_PERMISSIONS.

### USERS
- **Зачем:** аккаунт: e-mail, хэш пароля, роль, статус (F-01, F-22).
- **Почему:** здесь только данные для входа.
  - `UK_USR_EMAIL` — критерий F-01: на один e-mail нельзя завести два аккаунта.
  - `PASSWORD_HASH` хранит только хэш Argon2id или bcrypt (§9).
  - `STATUS` ACTIVE/BLOCKED — блокировка администратором.
  - `FAILED_LOGINS` — для ограничения попыток входа.
  - `CONSENT_AT` — согласие RODO при регистрации.

  При удалении аккаунта (F-04) каскадом удаляются профиль, прогресс, документы и доступы помощников.
- **Связи:** → ROLES. Ссылаются на неё: USER_PROFILES, USER_PROGRESS, USER_DOCUMENTS, HELPER_ACCESS (дважды), CHANGE_LOG, `VERIFIED_BY` у PROCEDURES и DOCUMENTS.

### CHANGE_LOG
- **Зачем:** журнал изменений: что, кто, когда, старое и новое значение (F-23). Сюда же пишутся действия помощника (§4.3) и отметки «zweryfikowano» (`ACTION = 'VERIFY'`, F-25).
- **Почему:** одна таблица для всех сущностей (`ENTITY_TYPE`, `ENTITY_ID`). Значения хранятся в CLOB, потому что описания процедур длинные. `USER_ID` с `SET NULL`: после удаления аккаунта автора запись журнала остаётся, а персональная связь исчезает.
- **Связи:** → USERS.

## Колонка 4. Работа клиента

### HELPER_ACCESS
- **Зачем:** приглашение помощника кодом или по e-mail, принятие и отзыв (F-16). Помощник видит только клиентов с активным доступом (§4.3, F-17).
- **Почему:** доступ — отдельная сущность со статусом PENDING/ACTIVE/REVOKED и датами. Согласие клиента записано явно, отзывается в любой момент, история сохраняется. `HELPER_ID` пуст, пока приглашение не принято. `CK_HLA_NOT_SELF` запрещает пригласить самого себя, `INVITE_CODE` уникален.
- **Связи:** `CLIENT_ID` и `HELPER_ID` → USERS. ← HELPER_NOTES.

### HELPER_NOTES
- **Зачем:** заметки помощника к шагу плана, которые видит клиент (F-18).
- **Почему:** заметка ссылается на доступ (`ACCESS_ID`), а не на пользователя. Так она существует только в рамках согласия клиента, а из доступа известны и клиент, и помощник.
- **Связи:** → HELPER_ACCESS, → PROCEDURES.

### USER_PROGRESS
- **Зачем:** статус каждого шага плана клиента — TODO / IN_PROGRESS / DONE / SKIPPED — и дата выполнения (F-12). `DONE_WITH_HELPER` означает, что шаг отмечен вместе с помощником (§4.3).
- **Почему:** ключ `(USER_ID, PROCEDURE_ID)` не зависит ни от профиля, ни от сценария. Поэтому после смены профиля план пересчитывается, а выполненные шаги остаются (F-03, §12). DONE и SKIPPED покрывают шаг, сделанный ещё до системы (§7). От `DONE_AT` считаются сроки «от предыдущего шага».
- **Связи:** → USERS, → PROCEDURES.

### USER_DOCUMENTS
- **Зачем:** какие документы у клиента уже есть (F-11). План пропускает шаги, которые выдают эти документы.
- **Почему:** хранится только факт наличия и срок годности. Номеров и сканов нет (§3, §6 п.9, RODO). `VALID_UNTIL` заполняется для документов с `HAS_EXPIRY = 1`.
- **Связи:** → USERS, → DOCUMENTS.

## Колонка 5. Сценарии и граф процедур

### LIFE_SITUATIONS
- **Зачем:** точка входа: «начинаю работу», «учусь», «открываю бизнес» (F-05). Пять сценариев MVP — это пять строк (§7).
- **Почему:** сценарий хранится в данных. Сценарии развития (рождение ребёнка, потеря работы) добавляются без изменения кода.
- **Связи:** ← SITUATION_PROCEDURES, ← USER_PROFILES.

### SITUATION_PROCEDURES
- **Зачем:** какие процедуры входят в жизненную ситуацию.
- **Почему:** связь M:N, потому что PESEL или NFZ входят в несколько сценариев. `SORT_ORDER` задаёт только порядок показа независимых шагов (F-08). Настоящую последовательность задаёт граф PROCEDURE_DEPENDENCIES.
- **Связи:** → LIFE_SITUATIONS, → PROCEDURES.

### PROCEDURES
- **Зачем:** административная процедура, узел графа. Это карточка из F-09: описание, учреждение, способ подачи, стоимость, срок, источник, дата проверки.
- **Почему:**
  - Метаданные актуальности хранятся прямо в строке (F-24): `SOURCE_ID`, `VERIFIED_AT`, `VERIFIED_BY`, `REVIEW_INTERVAL_DAYS`, `STATUS`. По ним строится список «do sprawdzenia» (F-25) и баннер при `STATUS = 'TO_CHECK'` (F-26).
  - Новая запись по умолчанию получает `TO_CHECK`: непроверенные данные не выдаются за актуальные (§11).
  - `DEADLINE_DAYS` + `DEADLINE_ANCHOR` задают сроки от дня приезда или от выполнения предыдущего шага (§7).
  - `CODE` — стабильный ключ для загрузки данных.
- **Связи:**
  - → INSTITUTIONS, OFFICIAL_SOURCES, USERS (`VERIFIED_BY`).
  - Ссылаются на неё: PROCEDURE_STEPS, PROCEDURE_DEPENDENCIES (дважды), AVAILABILITY_RULES, SITUATION_PROCEDURES, PROCEDURE_DOCUMENTS, USER_PROGRESS, HELPER_NOTES.

### PROCEDURE_STEPS
- **Зачем:** пошаговая инструкция внутри одной процедуры: записаться на визит, подать wniosek, забрать карту.
- **Почему:** шаги процедуры — не то же самое, что шаги плана. План состоит из процедур, а здесь детализация одной карточки. `UK (PROCEDURE_ID, STEP_NO)` не даёт номерам шагов повторяться.
- **Связи:** → PROCEDURES (CASCADE).

### PROCEDURE_DEPENDENCIES
- **Зачем:** рёбра графа: «процедура требует сначала выполнить другую» (F-06, F-07). Рекурсивный запрос по этой таблице строит порядок плана (§6 п.1, пример ниже).
- **Почему:**
  - Составной PK исключает дубли рёбер, а `CK_PDP_NOT_SELF` — ребро на саму себя.
  - `IS_BLOCKING = 1`: шаг заблокирован до выполнения (F-07). `IS_BLOCKING = 0`: порядок только рекомендован.
  - Цикл длиннее одного ребра через CHECK не поймать. Его проверяет приложение при сохранении (§6 п.5, §11), пример ниже.
- **Связи:** `PROCEDURE_ID` и `REQUIRED_PROCEDURE_ID` → PROCEDURES.

## Колонка 6. Учреждения и документы

### INSTITUTIONS
- **Зачем:** учреждения: Urząd Wojewódzki, ZUS, NFZ, Urząd Skarbowy, gmina (F-19).
- **Почему:** одно учреждение ведёт много процедур и выдаёт много документов, поэтому хранится один раз.
- **Связи:** ← INSTITUTION_OFFICES, ← PROCEDURES, ← DOCUMENT_ISSUERS.

### INSTITUTION_OFFICES
- **Зачем:** конкретные отделения: город, адрес, часы работы, телефон, ссылка на онлайн-запись (§10).
- **Почему:** у учреждения много отделений. `BOOKING_URL` заложен под карту отделений с записью (§13).
- **Связи:** → INSTITUTIONS (CASCADE).

### PROCEDURE_DOCUMENTS
- **Зачем:** какие документы нужны для процедуры (F-10).
- **Почему:** даёт условия AND/OR (§6 п.3) без отдельной таблицы групп. Документы с одинаковым `ALTERNATIVE_GROUP` взаимозаменяемы (OR), документы из разных групп нужны все (AND). Например, группа 1 — паспорт, группа 2 — договор **или** oświadczenie pracodawcy.
- **Связи:** → PROCEDURES, → DOCUMENTS.

### DOCUMENTS
- **Зачем:** справочник документов: что это, нужен ли присяжный перевод, есть ли срок годности (F-10).
- **Почему:** флаги `HAS_EXPIRY` и `NEEDS_SWORN_TRANSLATION` прямо из §8. Метаданные актуальности те же, что у PROCEDURES (F-24).
- **Связи:** → OFFICIAL_SOURCES, USERS (`VERIFIED_BY`). ← PROCEDURE_DOCUMENTS, DOCUMENT_ISSUERS, USER_DOCUMENTS.

### DOCUMENT_ISSUERS
- **Зачем:** где получить документ («miejsce uzyskania dokumentu», §8).
- **Почему:** связь M:N. Один документ выдают разные учреждения, одно учреждение выдаёт много документов.
- **Связи:** → DOCUMENTS, → INSTITUTIONS.

## Колонка 7. Источники и словарь

### OFFICIAL_SOURCES
- **Зачем:** официальные страницы, на которых основан контент: gov.pl, biznes.gov.pl, UdSC, ZUS, NFZ (§10).
- **Почему:**
  - Одна страница подтверждает много процедур и документов, поэтому источник — отдельная сущность.
  - URL уникален.
  - `LAST_CHECKED_AT` заложен под автоматическое отслеживание изменений страниц (§13).
  - Удаление источника обнуляет ссылки (`SET NULL`), но процедуры не трогает.
- **Связи:** ← PROCEDURES, ← DOCUMENTS, ← GLOSSARY_TERMS.

### GLOSSARY_TERMS
- **Зачем:** словарь польских административных терминов: zameldowanie, karta pobytu, JDG (F-14).
- **Почему:** термин и определение хранятся по-польски. Переводы идут через TRANSLATIONS (`ENTITY_TYPE = 'GLOSSARY_TERMS'`), как у остального контента. Термин уникален.
- **Связи:** → OFFICIAL_SOURCES.

## Как модель закрывает ключевые запросы

Порядок плана для жизненной ситуации (§6 п.1). Чем больше `DEPTH`, тем раньше выполняется шаг. Шаги с одинаковой глубиной можно делать параллельно (F-08). Фильтр по AVAILABILITY_RULES и USER_PROGRESS накладывается поверх.

```sql
WITH plan (procedure_id, depth) AS (
    SELECT sp.procedure_id, 0
    FROM situation_procedures sp
    WHERE sp.situation_id = :situation_id
    UNION ALL
    SELECT d.required_procedure_id, p.depth + 1
    FROM plan p
    JOIN procedure_dependencies d ON d.procedure_id = p.procedure_id
)
CYCLE procedure_id SET is_cycle TO 'Y' DEFAULT 'N'
SELECT procedure_id, MAX(depth) AS depth
FROM plan
GROUP BY procedure_id
ORDER BY depth DESC;
```

Проверка цикла перед сохранением ребра «`:procedure_id` требует `:required_id`» (§6 п.5). Если запрос вернул больше 0, ребро замкнёт цикл, и сохранение надо отклонить.

```sql
SELECT COUNT(*) AS creates_cycle
FROM (
    SELECT required_procedure_id AS procedure_id
    FROM procedure_dependencies
    START WITH procedure_id = :required_id
    CONNECT BY NOCYCLE PRIOR required_procedure_id = procedure_id
)
WHERE procedure_id = :procedure_id;
```

Список «do sprawdzenia» для панели администратора (F-25):

```sql
SELECT id, code, title, verified_at
FROM procedures
WHERE status = 'TO_CHECK'
   OR verified_at IS NULL
   OR verified_at + review_interval_days < SYSDATE;
```
